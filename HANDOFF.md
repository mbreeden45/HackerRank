# Handoff: Builder Prep offline study app

Read this first, then `DECISIONS.md`. Phases 1, 2 and 3 are built, committed and verified. What is left is learner testing and polish (see the end).

## Goal
A local, offline study app that prepares a complete beginner (no coding background, Python 3) for the HackerRank Builder assessment. Passing bar: 60 percent (draw one line at 60, no 70 line).

## Learner rules (apply to ALL content)
- Plain English first, then code. Define every symbol the first time it appears. One new idea at a time.
- Always show a worked example before asking the learner to try one.
- Use the same words as the question when answering.
- Encouraging, never condescending. No exclamation marks (verify.py enforces this in prose).
- Shaky areas: for loops over values vs positions, indexing and slicing, off-by-one (len vs last position vs range), %, == vs =, sliding window, two pointers, 2D grids.

## Hard requirements
- Fully offline. No build step, no frameworks, no accounts. Launch with `start.command` (python3 http.server on 127.0.0.1:8765, opens Chrome).
- Everything vendored in `vendor/` (Pyodide 0.26.4, sql.js 1.10.3, CodeMirror 5).
- Progress is saved in localStorage key `builderPrep.v1`.

How things fit together:
- `tools/c_kit.py` builds function-style Python problems from a list of typed parameters (ints, int, str, words, lines, grid). The locked main block, input format text and test input encoding are generated from that list.
- `build_content.py` runs every reference solution to produce hidden test outputs. `c_sql.py` runs every SQL solution with sqlite3 to produce `expected` rows, and asserts a hand-counted `expect_count`.
- Routes (all through `BP.routeHandlers` in `app.js`): `#/study/<id>` reading lessons, `#/quiz/<bigo|prompt>[/all|new|missed]`, `#/quizitem/<id>`, `#/sql`, `#/sqlproblem/<id>`, `#/next` (adaptive), `#/cards[/study[/<topic>]]`, `#/mock[/start[/<minutes>]|/resume]`.
- Mock exam debug clock: `#/mock/start/0.5` runs a 30 second exam, to test timer expiry. Without the number it is 90 minutes.
- Adaptive picker (`js/adaptive.js`): due reviews first (missed items return after 1, 3 and 7 days), then the weakest topic weighted by exam priority, then one level above the hardest mastered level. A coding problem counts as missed after 3 failed runs, after opening the full solution while unsolved, or when solved with 3 or more hints.
- Flashcards (`js/cards.js`): Again, Hard, Good, Easy with stored due dates. Cards that show code carry an executed `check`.
- Multiple-choice options are shuffled on screen in the diagnostic, lesson predict questions and quizzes.

## Known lessons learned
- The macOS python3 is 3.9, the browser's is 3.12. Avoid version-specific features. Error messages differ (see LITERALS in verify.py).
- Multiple-choice options must render with `white-space: pre-wrap` (already in css `.opt`). Anything new that shows code or output must do the same.
- Browser testing: serve with `python3 -m http.server 8765 --bind 127.0.0.1` and drive the page. After CSS or JS changes, reload.
- Project sits under `~/.cursor`, which some sandboxes cannot write to.
- Adding lessons to `lessons.json` changes the placement check: it only covers lessons without a `track` field (the Basics).

## Still open
- Offline use was not tested in real airplane mode. The browser network log shows only requests to 127.0.0.1, so it should work. Check by running one problem with Wi-Fi off after the first load.
- No real learner has used the content yet. The hard problems (`tp_three_sum`, `gr_islands`, `hm_subarray_sum`, `sw_at_most_k_distinct`, `sort_intervals`) and the written Prompt Engineering rubrics are the most likely to need wording changes after real use.
- Phase 1 has 44 problems in 14 lessons, and the placement check is 13 questions.
- Not built by design: SQL Advanced, System Design, Stakeholder Communication, heaps, greedy, a dashboard or scores chart, a printable cheat sheet, export and import backup.
